# V2.0 — Cryptographic pairing primitives

## Purpose

Add a small, independently testable cryptographic building block for the future phone-to-PC pairing flow. The implementation uses Node.js built-in Ed25519 and cryptographically secure random values. It is a protocol primitive and test fixture, not a live pairing service.

## Implemented

- Generate an in-memory Ed25519 device key pair.
- Export the public key and calculate its SHA-256 fingerprint.
- Create a short-lived challenge bound to a device ID, host ID, protocol version, nonce and requested scopes.
- Restrict requested scopes to READ_STATUS and READ_HEALTH.
- Sign the canonical challenge with the device private key.
- Verify the proof with the presented public key and return the public-key fingerprint.
- Reject malformed, expired, future-dated, overlong, tampered, wrong-key and unsafe-scope inputs.
- Add automated Node tests for the positive and negative cases.

## Deliberate limitations

This milestone does **not**:
- store or protect private keys using Android Keystore, TPM, DPAPI or another platform vault;
- authenticate the PC/host to the phone or replace certificate-validated TLS;
- issue access tokens or durable credentials;
- persist pending challenges or enrolled devices;
- provide durable replay protection or a one-time challenge-consumption ledger;
- start a network listener, open a firewall, bind to a LAN address or establish a VPN;
- expose project writes, shell, PowerShell, process launch, agent dispatch, publishing or deployment;
- connect to Quinn, Ollama or the desktop.

The private key remains an in-memory KeyObject in this module. A production Android client must use a reviewed native/platform key broker; it must not serialize private key material into localStorage or an ordinary browser database.

## Required next gates

1. Independent cryptographic and protocol review.
2. Select and implement a private transport with authenticated host identity and certificate validation.
3. Integrate a protected device-key provider on Android and a protected host identity/key provider on Windows.
4. Add server-side challenge state, one-time consumption, durable replay defense, credential issuance, rotation and revocation.
5. Implement a read-only host service with strict loopback/LAN policy, authenticated device middleware, rate limits and redacted audit records.
6. Run the complete Node suite and independent security review.
7. Perform physical Android Chrome/PWA and Windows host integration tests.
8. Obtain explicit Owner approval before any live pairing trial.

## Verification status

Source-level automated tests are included in this branch and must pass in GitHub Actions before review. No physical-device, host integration, live pairing or production security claim is made. The host remains disabled; agents remain planned; dispatch and remote execution remain prohibited.
