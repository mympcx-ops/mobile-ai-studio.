# V1.6 — Secure Device Pairing Protocol and Credential Lifecycle

**Status:** DESIGN ONLY / NOT IMPLEMENTED  
**Release posture:** HOLD — pairing, credential issuance, device enrollment, and live PC connection remain disabled.

## 1. Purpose and trust boundaries

V1.6 specifies what a future phone-to-PC pairing implementation must satisfy. The Android phone remains the user-facing command station; the PC is the backend host for Quinn/Ollama and approved studio services. Neither endpoint trusts identity claims supplied in an unauthenticated request.

This document is a requirements contract, not evidence that cryptography, transport security, device identity, or credential storage currently exists. The V1.3 contract validator, V1.4 in-process simulator, and V1.5 host-policy evaluator remain reference-only components.

## 2. Security invariants

1. Pairing is disabled unless the Owner explicitly opens a short-lived pairing window on the PC host.
2. The PC host binds only to literal loopback addresses by default. LAN access is not implied or authorized.
3. A phone is not trusted because it knows a device ID, pairing code, URL, or request field.
4. Pairing requires proof of possession of a one-time challenge over mutually authenticated encrypted transport in the eventual implementation.
5. Enrollment grants only minimum read-only health/status scope. It grants no project write, task dispatch, agent control, shell, filesystem, or execution rights.
6. The Owner must approve enrollment and every later privilege expansion. An agent, model, or phone UI cannot approve for the Owner.
7. Credentials are unique per device, independently revocable, and never displayed again after initial provisioning.
8. Lost, revoked, expired, or uncertain credentials are denied by default.
9. Secrets, pairing codes, private keys, access tokens, and full credential material must never appear in logs, screenshots, analytics, exports, PR comments, or chat.
10. Pairing success is not release approval and does not permit agent dispatch.

## 3. Roles

- **Owner:** Opens the pairing window, reviews device identity/fingerprint, approves or rejects enrollment, and may revoke any device.
- **PC host:** Generates and validates the challenge, binds approval to the exact pending device key, enforces scopes, and records redacted audit events.
- **Phone command station:** Protects its device key, verifies host identity, proves challenge possession, and stores any issued credential in platform-protected storage.
- **Independent reviewer:** Reviews the actual implementation, threat model, test evidence, and credential lifecycle before release gates can be lifted.

## 4. Proposed enrollment sequence

1. Owner opens a short-lived pairing window from the trusted PC-local control surface. Default state is CLOSED.
2. Host creates a cryptographically random, single-use challenge with strict expiry, bound to the pending phone public key, pairing session, host identity, and requested scope.
3. Phone verifies host identity through a separately displayed fingerprint or equivalent authenticated channel. A QR code may transport public session metadata but is not proof of identity by itself.
4. Phone proves possession of its private key by signing a transcript containing protocol version, host identity, phone public-key fingerprint, challenge ID, expiry, requested scope, and session binding.
5. Host verifies proof, expiry, one-time use, protocol version, and exact transcript binding. It rejects replay, mismatched keys, altered scopes, stale challenges, and unknown protocol versions.
6. PC displays device label, public-key fingerprint, requested permissions, and consequences to the Owner.
7. Owner explicitly approves or rejects. Approval is bound to the exact public key and exact scope; it cannot be reused for another device or scope.
8. Only after approval does the future implementation issue a unique device credential. It is delivered once over the authenticated encrypted channel and stored using platform-protected storage.
9. Host records a redacted enrollment result. Phone confirms enrolled host identity and read-only scope.
10. Pairing window closes automatically after expiry or successful use. Unused challenges are invalidated.

No part of this sequence is implemented by the current repository.

## 5. Challenge requirements

A future implementation MUST:
- Use a cryptographically secure random number generator supplied by the platform/runtime.
- Use at least 256 bits of challenge entropy.
- Enforce a short expiry (recommended maximum: 5 minutes).
- Bind the challenge to one pairing session, one host identity, one phone public key, one protocol version, and one exact requested scope set.
- Mark a challenge consumed atomically before returning success.
- Reject reuse, expiry, clock anomalies outside defined tolerance, malformed encodings, and transcript substitution.
- Never use a user-entered short numeric PIN as the sole authentication factor.
- Rate-limit attempts and apply bounded delays without creating a denial-of-service path for enrolled devices.

A challenge ID is an identifier, not a secret. A challenge value is secret until consumed and must never be logged.

## 6. Credential lifecycle

| State | Meaning | Permitted transition |
|---|---|---|
| NOT_PAIRED | No enrolled credential exists | Owner opens pairing window |
| PAIRING_WINDOW_OPEN | Host accepts enrollment attempts | Challenge issued, timeout, or Owner closes |
| CHALLENGE_ISSUED | One device/session challenge is pending | Proof accepted, rejected, or expired |
| OWNER_REVIEW_PENDING | Proof verified; Owner decision required | Owner approves or rejects |
| ACTIVE_READ_ONLY | Unique device credential is valid for read-only health scope | Rotate, revoke, expire, or suspend |
| ROTATION_PENDING | Replacement credential requested | Owner-approved rotation completes or is cancelled |
| REVOKED | Credential permanently invalid | New pairing required |
| EXPIRED | Credential validity ended | New pairing required |
| SUSPENDED | Host blocks use pending investigation | Owner-authorized recovery or revoke |

Rules:
- Revocation takes effect server-side immediately and invalidates active sessions.
- Revocation is per-device and does not require deleting other devices.
- Rotation creates a new credential and invalidates the old credential atomically. No overlap is allowed unless a separately documented, short, explicitly approved migration window is essential.
- Device rename does not change identity; identity is bound to the key fingerprint, not display label.
- Reinstalling the phone app or losing protected key material requires new pairing.
- Backup/export must never export private keys or reusable bearer credentials.
- A revoked device cannot self-reactivate.
- Unknown or inconsistent lifecycle state is DENY.

## 7. Credential storage and transport

**Phone**
- Use Android Keystore-backed, non-exportable key material where supported.
- Prefer hardware-backed protection when available and report the actual security level honestly.
- Never put credentials in localStorage, IndexedDB, ordinary preferences, exported backups, source code, URLs, clipboard, or logs.
- Clear app-held session material on logout, revocation notice, and process recovery.

**PC**
- Store verifier/public-key and credential metadata separately from secrets.
- Protect private material using OS-provided secret storage or an equivalent reviewed mechanism.
- Restrict file permissions and service identity.
- Never store raw credentials in configuration files or source control.
- Support immediate revocation and key rotation.

**Transport**
- Use modern TLS with certificate/host identity validation and no trust-on-first-use without an explicit verified fingerprint step.
- Reject invalid, expired, mismatched, or downgraded certificates.
- Never disable certificate validation to make pairing work.
- Use authenticated sessions and replay protection on every protected request.

## 8. Failure behavior

Every failure is fail-closed. The UI must distinguish NOT_CONNECTED, PAIRING_WINDOW_CLOSED, CHALLENGE_EXPIRED, HOST_IDENTITY_UNVERIFIED, DEVICE_PROOF_REJECTED, OWNER_APPROVAL_REQUIRED, DEVICE_REVOKED, CREDENTIAL_EXPIRED, AUTHENTICATION_FAILED, INSUFFICIENT_SCOPE, and HOST_UNAVAILABLE.

A timeout, app restart, PC restart, or ambiguous response must not silently enroll a device or broaden permissions. The phone returns to disconnected/unknown and requires a fresh authenticated status check.

## 9. Audit requirements

Record only redacted metadata: event ID and timestamp; host instance identifier; pseudonymous device identifier and public-key fingerprint; requested and granted scope names; lifecycle transition and result code; Owner approval decision reference; software/protocol version.

Never record challenge values, private keys, bearer credentials, authorization headers, or raw pairing payloads. Audit storage must be access-controlled, tamper-evident, bounded/rotated, and tested for secret leakage.

## 10. Explicitly excluded capabilities

Pairing does not authorize agent activation/dispatch, Quinn/Ollama prompts or model management, project writes or file transfer, shell/PowerShell/arbitrary command/path/URL fetch, installation/publishing/deployment/system changes, hardware control, racing/simulator control, or any action not separately specified, reviewed, tested, and approved.

- [ ] Android Keystore behavior and recovery tested on physical devices.
