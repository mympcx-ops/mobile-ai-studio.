# V1.3 PC Bridge Protocol Contract and Security Test Plan

Status: CONTRACT + LOCAL UNIT TESTS ONLY. This is not a running PC service, cryptographic authenticator, TLS implementation, or production security approval.

## Scope and topology
- Phone/PWA remains the only user-facing command station.
- PC host owns the bridge listener, device authentication, authorization, replay protection, audit log and any future execution gate.
- Quinn, STARNet and Ollama are not exposed directly to the network.
- Initial protocol scope is read-only status and proposal creation. No remote execution endpoint is defined.

## Transport and identity requirements
1. Bind only to an explicitly configured private interface or authenticated reverse tunnel. Never expose an unauthenticated listener to the public internet.
2. Require TLS 1.3 where supported; reject cleartext HTTP outside a loopback-only development harness.
3. Authenticate a paired device using a revocable, short-lived credential held in Android Keystore / platform secure storage where available. Never put secrets in localStorage, URLs, source control, logs, screenshots or backups.
4. Pairing begins on the PC with a one-time challenge. Owner confirms the device name, fingerprint and exact scopes on the PC display.
5. PC service maintains device revocation, credential expiry, rate limits and server-side authorization. A phone-provided role, scope, approval or device label is never trusted as identity proof.

## Version 1 request envelope
The canonical JSON request has these required fields:
- `protocol`: exact string `mobile-ai-studio-bridge/1`.
- `requestId`: unique request identifier (8–128 safe characters).
- `deviceId`: paired device identifier.
- `timestamp`: Unix epoch milliseconds; maximum clock skew 60 seconds.
- `nonce`: cryptographically random, single-use value (at least 16 URL-safe characters).
- `action`: exact allowlisted action.
- `args`: bounded JSON object; maximum 16 KiB.

Allowed actions and required scopes:
| Action | Scope | Behavior |
|---|---|---|
| READ_STATUS | READ_STATUS | Return observed service health only |
| READ_PROJECT | READ_PROJECT | Return explicitly permitted project metadata |
| PROPOSE_TASK | PROPOSE_TASK | Create a proposal; never dispatch |
| PROPOSE_ACTION | PROPOSE_ACTION | Create an approval request; never execute |
| ADMIN_PAIRING | ADMIN_PAIRING | PC-side owner pairing/revocation workflow only |

No wildcard scope. No generic shell, PowerShell, Python, arbitrary filesystem path, URL fetch, plugin invocation, model prompt execution or command endpoint. `EXECUTE_APPROVED` is intentionally not part of v1.

## Response envelope
Every response includes `protocol`, `requestId`, `serverTime`, `serviceVersion`, `status`, and `observedAt`. Status values are `OK`, `REJECTED`, `STALE`, `UNAVAILABLE`, or `ERROR`. Health values must be observed, timestamped facts. Unknown or stale values remain UNKNOWN / NOT CONNECTED, never green by inference.

## Server validation order
1. Enforce request body and header size limits before parsing.
2. Require TLS and authenticate the device credential before trusting request identity.
3. Validate protocol version, schema, field types, timestamp, action allowlist and argument size.
4. Resolve device status and scopes from the server-side pairing registry.
5. Check nonce uniqueness in a durable, atomic replay store; reject replay and fail closed if the store is unavailable.
6. Apply per-device and per-action rate limits.
7. Authorize the exact action and arguments; append a redacted audit event.
8. Return only the minimum response fields needed by the phone.

The `bridge/contract.cjs` file is a small Node.js reference validator for envelope shape, trusted-principal scope checks and an in-memory nonce ledger. It is intentionally not production-safe: its nonce ledger is process-local and non-durable. Production must use an atomic durable store and cryptographically authenticated transport/credentials.

## Approval binding for any future executable action
Execution is out of scope for this protocol version. If a later version proposes execution, approval must bind a canonical SHA-256 digest of the exact action, normalized arguments, target, risk classification, requester, expiry and rollback plan. The server must re-check the digest, approver authorization, expiry and one-time approval token immediately before execution. Any changed argument invalidates approval. High-impact actions require a second Owner confirmation. No frontend-only approval record can authorize PC execution.

## HOLD and emergency stop
Phone-side HOLD is a UI workflow guard only. A future PC service must independently enforce a server-side HOLD before any operation and expose a PC-local emergency stop. Loss of phone connectivity must never disable PC-side safeguards.

## Local security tests
Run from repository root with Node.js 18 or newer:
```sh
node --test tests/bridge-contract.test.cjs
```
The tests cover protocol version, timestamp skew, nonce shape and replay, action allowlist, generic execution-field rejection, argument type/size, authenticated principal, device identity, least-privilege scope and fail-closed behavior.

These tests are unit tests of the reference contract, not penetration testing, TLS verification, Android Keystore validation, durable replay-store testing or independent security certification. A reviewer other than the builder must inspect the contract and test results before any real PC listener is enabled.
