# V1.8 — Threat Model and Security Acceptance Contract

**Status:** REVIEW BASELINE / NOT A SECURITY CERTIFICATION  
**Scope:** future phone-to-PC read-only status connection only.  
**Current implementation:** no real network endpoint, cryptographic identity, credential, durable replay store, or live health provider exists.

## 1. Assets to protect

- Owner authority and approval decisions.
- PC host identity and integrity.
- Phone device identity and any private key/credential.
- Quinn/Ollama and local model services, which must not be directly exposed.
- Project files, prompts, model data, local paths, environment variables and system metadata.
- Planned agent definitions and all existing application data.
- Audit integrity and accurate connection/health state.

## 2. Security objectives

1. Only the explicitly enrolled phone can authenticate.
2. Host identity is verified before the phone sends credentials or accepts status.
3. Pairing is closed by default and requires a local Owner action plus a separate enrollment approval.
4. First connection is read-only and limited to `READ_STATUS` / `READ_HEALTH`.
5. A network path cannot broaden permissions or bypass server-side authorization.
6. Every protected request is replay-resistant and bounded.
7. Revocation and disconnect stop subsequent requests; stale data is never presented as live.
8. No secret or unnecessary host/project data is disclosed in logs or diagnostics.
9. Failure, ambiguity, clock anomalies, missing fields and unknown state fail closed.
10. No remote execution or agent dispatch is introduced by the connection milestone.

## 3. Trust boundaries and adversaries

| Boundary / actor | What may go wrong | Required defense |
|---|---|---|
| Untrusted LAN peer | Scans port, sends malformed or hostile requests | Narrow firewall scope, TLS, auth, schema/size/rate limits, default deny |
| Rogue access point / network interception | Impersonates host or observes/modifies traffic | Strict host identity validation; no plaintext fallback; reject identity changes |
| Stolen or lost phone | Attempts to reuse enrolled identity | Per-device revocation, protected key, session invalidation, re-pair after key loss |
| Malicious or compromised browser origin | Reads browser data or invokes available UI APIs | Minimize secrets in browser; CSP/origin controls; no credential in localStorage; consider native key broker |
| Replayed or delayed request | Repeats an earlier authenticated operation | Server-side durable replay protection, expiry, sequence/nonce policy, bounded clock tolerance |
| Malicious request body | Forges device ID, scopes, Owner approval, paths or commands | Principal derived only from verified server-side credential; strict allowlisted schemas |
| Compromised PC user process | Reads host secrets or tampers with health output | Dedicated least-privilege service identity, OS ACLs, minimal provider, independent host security review |
| Dependency compromise | Malicious or vulnerable crypto/network library | Maintained dependencies, pinned versions, advisory monitoring, SBOM and reproducible builds |
| Accidental configuration | Wildcard bind, broad firewall, debug logging, public exposure | Disabled-by-default startup, exact interface validation, config lint, local disable, Owner review |

## 4. Abuse cases and mandatory outcomes

| Abuse case | Expected outcome |
|---|---|
| Phone connects while pairing window is closed | Deny; no challenge or enrollment |
| Unknown device presents a known device ID | Deny; identity is key/credential-bound |
| Request body claims `ownerApproved=true` | Ignore claim; trusted server-side approval state only |
| Request body adds `EXECUTE`, `DISPATCH_AGENT`, write or admin scope | Reject; no privilege change |
| Challenge expired, reused, or bound to another key/session | Deny and record redacted failure |
| Host certificate/fingerprint changes unexpectedly | Stop; require explicit verified recovery |
| Invalid TLS, downgrade, expired identity or untrusted issuer | Abort; no insecure fallback |
| Credential revoked, expired or suspended | Deny immediately; invalidate sessions |
| Replay store unavailable or uncertain | Deny protected request; never fall back to memory-only permissive mode |
| Health provider requests shell/process/path access | Reject implementation; health read must remain side-effect-free |
| Response malformed, stale, sequence rollback or missing fields | Reject/mark DEGRADED, STALE or UNKNOWN |
| PC sleeps/restarts or phone changes network | Disconnect and re-authenticate; no cached green state |
| Host service receives excessive traffic | Rate-limit; bounded resource use; preserve local disable path |
| Firewall or bind configuration is broader than approved | Do not start; require Owner correction |

## 5. Minimum read-only API contract

Allowed routes and fields are to be specified in a later implementation contract. At minimum:
- A health read is an explicit, authenticated, bounded request.
- The host derives device identity and scopes from verified server-side state.
- The provider reads only a fixed list of health signals.
- The response identifies `LIVE_HOST` versus `SIMULATOR_ONLY`, includes host-generated observation time and freshness threshold, and reports unknown states honestly.
- The provider cannot accept arbitrary commands, paths, process names, URLs, prompts or query expressions.
- No request changes host state, wakes an agent, starts a model, dispatches a task, writes a project, or changes configuration.

## 6. Audit and privacy contract

Audit events should record event type, pseudonymous device identifier, outcome, host instance identifier, timestamp, request correlation ID and minimal failure category. Do not record private keys, challenge secrets, bearer tokens, raw authorization headers, full request bodies, prompt contents, absolute paths, environment variables, local usernames or unnecessary IP history.

Logs must be bounded, access-controlled, rotated, and protected against silent modification. A log sink failure must not silently disable authorization or convert a denied request into an allowed one. Diagnostics must be previewed and redacted before any user-approved export.

## 7. Operational controls

- Service disabled by default; loopback-only in development.
- No public internet listener, router port forwarding or UPnP.
- No automatic firewall broadening or interface fallback.
- No direct exposure of Ollama or Quinn APIs.
- No secret-bearing URL, query string, browser localStorage, clipboard, screenshot, source file or repository artifact.
- No background reconnection after user disconnect.
- Bounded reconnect backoff; fresh identity and authentication checks on reconnect.
- Immediate local disable and per-device revocation.
- Separate dev/test data and host identity from any future production identity.

## 8. Evidence required before a live read-only trial

- [ ] Tested Android client key creation, protected storage claim, loss/reinstall recovery and revocation.
- [ ] Tested host identity verification and rejection of changed/invalid certificates.
- [ ] Independent review of selected protocol and all cryptographic library choices.
- [ ] Tests for replay, expiry, clock skew, duplicate requests, malformed payloads and storage failure.
- [ ] Tests proving the authenticated principal comes from trusted server state, not request JSON.
- [ ] Tests for every denied scope and lifecycle state.
- [ ] Proof that the health provider has no shell, process launch, filesystem traversal, model prompt, telemetry or write side effects.
- [ ] Firewall/bind inspection showing only the exact Owner-approved interface and phone are reachable.
- [ ] Redaction, retention and audit-integrity review.
- [ ] Physical Android Chrome/PWA acceptance, including sleep/wake, Wi-Fi change, offline, browser data clear and app restart.
- [ ] Independent security reviewer sign-off on actual code and configuration.
- [ ] Owner approval naming device, interface, scope, duration, and rollback procedure.
