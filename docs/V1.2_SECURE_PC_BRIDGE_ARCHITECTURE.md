# V1.2 Secure PC Bridge — Architecture and Threat Model

Status: DESIGN ONLY. No endpoint, credentials, tunnel, pairing or live connection has been created.

## Intended topology
- Android PWA: user-facing control surface.
- PC service: local backend host for Quinn, Ollama, agent construction, validation and approved local tools.
- Network transport: authenticated encrypted channel; the app must not expose Ollama directly to the public internet.
- Owner approval: server-side authorization gate for consequential operations.

## Pairing requirements
1. Pairing begins from the PC service with a short-lived, single-use pairing challenge.
2. Owner confirms the displayed device identity and pairing request.
3. Exchange a revocable device credential using a secure transport and platform-protected storage where available.
4. Never put pairing secrets in source control, URLs, logs, screenshots, localStorage or exported backups.
5. Provide revoke-all and per-device revocation from the PC.

## Request envelope
Every request must include a unique request ID, device identity, timestamp, nonce, action name, bounded arguments and an authorization context. Server rejects expired timestamps, replayed nonces, unknown actions, invalid schemas and unpaired devices.

## Permission model
- READ_STATUS: narrowly scoped health and connection state.
- READ_PROJECT: approved project metadata only.
- PROPOSE_TASK: create a proposal, not dispatch.
- PROPOSE_ACTION: create an approval request, not execute.
- EXECUTE_APPROVED: server verifies the exact approved payload, approver, expiry and one-time approval token before execution.
- ADMIN_PAIRING: owner-only pairing and revocation.

Default deny. No wildcard tool access. No arbitrary shell, PowerShell, filesystem path, URL fetch, or command execution endpoint.

## Approval binding
Approval must be bound to a canonical hash of the exact action and arguments, target, risk summary, expiry, rollback plan and requester. Any payload change invalidates approval. Require a second confirmation for high-impact actions. Log who approved, what was approved, when it was executed, result and rollback status.

## Audit and reliability
- Append-only server-side audit log with request/approval/result correlation.
- Redact secrets and sensitive payloads.
- Rate limits, payload size limits, schema validation and explicit timeouts.
- Health response reports observed facts, timestamp and service version; never infer agent readiness from process existence.
- Disconnected or stale health state must display UNKNOWN / NOT CONNECTED, not green.
- HOLD must be enforced by the PC service for actual execution; phone-only HOLD is not a backend kill switch.

## Rollout gates
1. Threat-model review.
2. Read-only status endpoint prototype.
3. Independent security review and replay/authorization tests.
4. Proposal-only endpoint.
5. Human-approved, allowlisted actions in a synthetic sandbox.
6. Independent validation.
7. Owner approval before any production integration.

This design does not authorize implementation of remote execution. Any future executable action requires a separately reviewed allowlist, explicit Owner approval and a tested rollback path.
