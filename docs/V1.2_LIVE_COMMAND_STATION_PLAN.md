# Mobile AI Studio V1.2 — Live Command Station

Status: DEVELOPMENT PLAN / NOT IMPLEMENTED
Target branch: feature/v1.2-live-command-station
Base: main

## Mission

Evolve the existing phone-first Mobile AI Studio into a dependable AI Operations Command Station while preserving the working V1.0 foundation and the merged V1.1 Command Center.

## Non-negotiable architecture

- Android phone is the primary user-facing command surface.
- The PC is a backend host for models, agent building, validation, and approved execution; it is not the primary user interface.
- Preserve the canonical organization: 29 agents plus six Floor Director / Independent Validator oversight roles.
- Preserve the hierarchy: Owner -> Secretary approval gate -> Studio Watchdog / COO -> Floor Director -> Manager -> Agents, with independent validation and reporting.
- Human approval is required before consequential actions, external writes, activation, publishing, or deployment.
- Builders do not validate their own work. Independent validators report separately.
- Existing V1.0 screens, data, installability, offline shell, backup/export, and working navigation must not regress.
- Quinn and Ollama must remain explicitly NOT CONNECTED until an actual authenticated, tested connection exists.
- No agent is considered active merely because it exists in the catalog.

## Delivery phases

### Phase 0 — Baseline protection and inventory
- Record the current main baseline and its existing files.
- Map V1.0 and V1.1 screens, scripts, storage keys, service-worker cache, manifest, and export/clear-data behavior.
- Define regression checks before changing shared code.
- Keep all V1.2 work on this feature branch until owner review.

### Phase 1 — Command Station shell
- Create a mobile-first command home with clear status indicators and one-handed navigation.
- Provide explicit states: LOCAL, CONNECTED, OFFLINE, SIMULATED, NOT CONFIGURED, and ERROR.
- Never display simulated or stale data as live telemetry.
- Keep the existing V1.0 Home, Chat, Projects, Agent Factory, Validation, and Settings accessible.

### Phase 2 — Organization and role operations
- Complete the 35-role Directory and Galaxy navigator.
- Preserve role mission, responsibilities, floor, manager, reporting line, permissions, dependencies, builder status, validation status, and lifecycle state.
- Provide full role detail windows and clear planned/not-started labels.
- Preserve all 29 agents and six oversight roles; do not silently rename, omit, duplicate, or activate roles.

### Phase 3 — Work management
- Improve tasks with owner, priority, status, dependencies, due date, evidence, and audit history.
- Add a communications inbox with sender, recipient, timestamp, priority, delivery state, and escalation.
- Until a backend exists, label records LOCAL DRAFT / NOT SENT.
- Add approvals with proposal scope, risk, evidence, decision, approver, timestamp, and explicit non-execution behavior.
- Add a global HOLD control that blocks new approved work dispatch once dispatch exists. Before backend integration, label it LOCAL HOLD ONLY and do not claim it stops running processes.

### Phase 4 — Independent validation and audit
- Add validation plans, test cases, evidence references, reviewer identity, outcome, blockers, and retest history.
- Prevent self-approval in the workflow design.
- Distinguish NOT RUN, IN PROGRESS, PASS RECORDED, NEEDS WORK, BLOCKED, and VERIFIED.
- A locally entered PASS is not a verified result until its evidence and reviewer are independently checked.
- Keep an append-oriented event history for consequential changes.

### Phase 5 — PC backend bridge
- Design a secure, authenticated phone-to-PC bridge with explicit pairing and revocation.
- Use least-privilege, scoped capabilities, request IDs, expiry, replay protection, and an auditable approval token for sensitive actions.
- Do not expose Ollama or agent tools directly to the public internet.
- Report backend heartbeat and hardware telemetry only when actually received and timestamped.
- Separate read-only health inspection from task dispatch and tool execution.

### Phase 6 — Quinn / Ollama integration
- Integrate only after bridge authentication, authorization, logging, and failure handling pass independent tests.
- Initially permit read-only status and controlled question/response workflows.
- Keep agent creation, tool access, file writes, activation, publishing, and deployment disabled until separately approved and validated.
- Never claim Quinn is connected without a successful live handshake and a visible, timestamped connection state.

### Phase 7 — Phone QA and release candidate
- Test on Android Chrome: navigation, touch targets, role details, storage persistence, import/export, clear-data confirmation, offline launch, and update behavior.
- Test narrow screens and accessibility labels/keyboard focus.
- Test backup compatibility and migration from existing V1.0/V1.1 local storage without data loss.
- Run script syntax checks and documented regression tests.
- Publish a V1.2 release candidate only after owner approval; do not publish a release automatically.
