# V1.8 — Phone-to-PC Transport and Trust-Boundary Decision

**Status:** ARCHITECTURE DECISION / NOT IMPLEMENTED  
**Release posture:** HOLD — no listener, firewall rule, LAN bind, tunnel, certificate, credential, or live connection is created by this document.

## 1. Decision summary

The Android phone and Windows PC are different network endpoints. A PC service bound to `127.0.0.1` is reachable only from that PC; it is not a phone-to-PC transport. The project must not quietly change the host from loopback to a LAN or wildcard bind to make the phone UI appear connected.

V1.8 establishes a transport boundary and a gated evaluation plan. It deliberately does **not** select or deploy a production transport until a physical Android/browser capability test and independent security review establish that the chosen client can protect device identity and validate the host.

**Recommended evaluation order:**
1. Prototype the phone client capability boundary using Android Chrome/PWA and, if required, a separately packaged Android shell with platform-backed key storage.
2. Evaluate a same-private-LAN path using HTTPS/TLS 1.3, explicit host identity verification, per-device authentication, and a Windows Firewall allowlist restricted to the Owner-approved phone.
3. Evaluate a private overlay network only if the same-LAN path is impractical. Treat its control plane, account, device enrollment, routing, and vendor dependency as additional trust boundaries.
4. Keep the PC host disabled and loopback-only until the Owner explicitly approves a separately reviewed live-connection trial.

This is an evaluation recommendation, not authorization to bind to a LAN, install a VPN, open a firewall port, or expose a service.

## 2. Why loopback-only cannot connect the phone

- `127.0.0.1` and `::1` always refer to the device making the request.
- On the PC, loopback protects the host service from other devices but prevents the phone from reaching it.
- A phone-to-PC connection therefore needs a routable path: a private LAN interface, a private overlay interface, or a physically mediated transfer. Each adds a trust boundary.
- A wildcard bind (`0.0.0.0` or `::`) is not an acceptable shortcut.
- A successful TCP or HTTPS connection alone does not authenticate the phone, establish Owner approval, or authorize a health read.

## 3. Transport options

| Option | Advantages | Risks / costs | V1.8 disposition |
|---|---|---|---|
| PC loopback only | Smallest exposure; useful for PC-local development | Phone cannot reach PC loopback | Keep as default; not a phone transport |
| Same private LAN + HTTPS | No third-party relay required; direct phone-to-PC path | LAN exposure, changing phone IP, router trust, firewall configuration, certificate identity and browser client-auth constraints | First transport to prototype; disabled until Owner approval |
| Private overlay (for example, a WireGuard-based deployment) | Encrypted routed path without opening a public inbound port in common configurations | Additional software/account/device enrollment, routing and control-plane trust; setup and recovery complexity | Contingency evaluation only; never silently install or enable |
| Public internet listener / port forwarding | Broad reachability | Unnecessary attack surface and exposure | Prohibited for this project |

## 4. Browser and device-key reality

The current user interface is a phone-first web application. A browser PWA must not be described as having Android Keystore protection unless a tested native integration actually provides it.

- WebCrypto can provide cryptographic operations in secure contexts, but a non-exportable browser key is not by itself proof of hardware-backed Android Keystore storage.
- Browser-origin storage can be cleared, evicted, backed up, restored, or lost with browser/app data. Recovery must require re-pairing rather than silently reconstructing device identity.
- Client-certificate selection and private-key integration vary across browser and packaging models. Do not assume Android Chrome PWA can perform mutual-TLS client authentication in the exact way a native application can.
- If physical testing shows that the PWA cannot meet key-protection or client-authentication requirements, keep the PWA as the user interface and evaluate a thin Android native shell/companion for key operations. Do not weaken authentication to preserve a pure-PWA implementation.
- Hardware-backed status must be measured and reported; never infer it from the presence of a key API.

## 5. Required logical architecture

Separate the system into replaceable, independently testable boundaries:

1. **Phone UI:** presentation, Owner-initiated connect/disconnect, status freshness and explicit simulator/live labeling.
2. **Phone identity provider:** key generation, protected storage, signing/client-auth operations, revocation cleanup. No secrets in localStorage, URLs, logs, clipboard, exports or source control.
3. **Transport adapter:** loopback development adapter, future same-LAN adapter, or future private-overlay adapter. A transport adapter cannot grant permissions.
4. **PC TLS endpoint:** disabled by default; exact interface/port configuration; host identity verification; bounded request sizes/timeouts/rates.
5. **Authentication middleware:** validates device proof/credential and resolves the principal from trusted server-side state. Never trust identity, scope or Owner-approval fields from request JSON.
6. **Authorization service:** default deny; checks active device lifecycle and exact minimum scope for every request.
7. **Read-only health provider:** returns a minimized, timestamped allowlisted snapshot without shell, process launch, arbitrary filesystem access, prompts, telemetry collection or writes.
8. **Redacted audit and replay store:** durable, bounded, integrity-protected records; no secrets or unnecessary personal data.
9. **Owner control surface:** pairing window, device approval, revocation, host enablement and emergency disable remain explicit Owner actions.

No layer may bypass another. A transport connection is not authorization. Authentication is not Owner approval. Owner approval is not permission to execute.

## 6. Host exposure controls for any future trial

A future trial requires all of the following, separately evidenced:
- Host remains disabled by default and starts only through an explicit local Owner action.
- Bind to one explicitly selected private interface, never wildcard; loopback remains the default.
- Windows Firewall inbound rule is limited to the exact selected port, private profile, and Owner-approved phone address where stable and practical.
- No router port forwarding, UPnP mapping, public DNS, public listener, or public relay.
- TLS 1.3 with strict host identity validation; no disabled certificate checks and no silent trust-on-first-use.
- Device authentication and server-side scope enforcement on every request.
- Rate, size, timeout, replay, and malformed-input controls.
- A one-action local disable path and tested revocation behavior.
- An independent reviewer inspects actual configuration and traffic before any live trial.
- Owner explicitly approves the exact host interface, transport, device, permission scope, duration, and rollback plan.

If the phone address changes or host identity changes unexpectedly, stop and require a fresh verification. Never broaden the firewall rule automatically.

## 7. Protocol and cryptography policy

- Do not invent a cryptographic handshake, key derivation scheme, signature transcript, or custom cipher suite.
- Select maintained, reviewed platform/library implementations after the client capability prototype.
- Prefer standard TLS 1.3 and established device-authentication mechanisms supported by the selected Android client and PC runtime.
- Define certificate issuance, renewal, revocation, pinning/rotation, clock tolerance, replay persistence and recovery before writing production code.
- Pin a host identity only through an explicit verified channel; a QR code may carry public metadata but is not proof by itself.
- If mutual TLS is selected, verify real Android client compatibility before committing the architecture. If an application-level credential is selected instead, use an established, reviewed standard and bind it to the authenticated transport; do not create a bespoke token protocol.
- Dependency selection requires maintenance activity, supported runtime versions, security advisories, license compatibility, reproducible installation and an update/rollback plan.

## 8. Data minimization

The first real connection remains limited to `READ_STATUS` and `READ_HEALTH`. No project content, file listing, telemetry stream, prompt history, environment variables, process command lines, local usernames, absolute paths, agent controls, write operations, or execution endpoints are in scope.

Health results are ephemeral by default, timestamped by the host, and shown as STALE/UNKNOWN/DISCONNECTED when freshness or connection cannot be established. Synthetic simulator data must never be represented as live host data.
