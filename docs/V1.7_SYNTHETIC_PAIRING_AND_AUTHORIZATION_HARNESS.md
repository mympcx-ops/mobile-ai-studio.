# V1.7 — Synthetic Pairing and Read-Only Authorization Harness

**Status:** IMPLEMENTED TEST HARNESS / SIMULATOR ONLY  
**Security posture:** NO REAL PAIRING, CREDENTIALS, CRYPTOGRAPHY, NETWORK, OR HOST ACCESS.

## Purpose

V1.7 turns the V1.6 pairing and read-only health design into an executable, deterministic test harness. It allows the team to test the intended lifecycle and UI state transitions before implementing cryptography or a live service.

## Files

- `bridge/pairing-simulator.cjs` — in-memory pairing lifecycle and health-state simulator.
- `tests/pairing-simulator.test.cjs` — tests for Owner gates, challenge expiry, synthetic proof outcomes, enrollment approval/rejection, read-only scopes, revocation, and stale/disconnected health states.

## Exercised lifecycle

`CLOSED → PAIRING_WINDOW_OPEN → CHALLENGE_ISSUED → OWNER_REVIEW_PENDING → ACTIVE_READ_ONLY → REVOKED`

Rejected and expired challenges cannot be reused. Enrollment is not active until a separate Owner approval. Revocation removes all read-only scopes in the simulator.

## Deliberate limitations

- The `proofValid` test input is a fixture, not signature verification.
- Challenge identifiers are synthetic labels; no challenge secret is generated.
- No credential or token is issued.
- No cryptography, TLS, sockets, HTTP listener, persistence, Android Keystore, PC filesystem, process, telemetry, Quinn, or Ollama access exists.
- The harness cannot dispatch agents, execute commands, write projects, or change the host.
- All outputs are labeled `SIMULATOR_ONLY`.

## Validation

Run with Node.js 22:

```sh
node --test tests/*.test.cjs
```

The repository workflow already runs all `*.test.cjs` files. A passing harness verifies only the synthetic state machine and existing reference tests. It is not a security review or production readiness claim.

## Exit criteria before real implementation

1. Independent review of the V1.6 protocol and this test model.
2. Choose and document an established cryptographic protocol/library; do not design custom cryptography.
3. Define Android and PC key protection and recovery behavior.
4. Implement a separate isolated development host with loopback-only binding.
5. Add real TLS identity validation, authenticated principals, durable replay protection, rate limits, and redacted audit.
6. Pass negative tests proving pairing cannot grant write, dispatch, or execution scopes.
7. Physical Android acceptance and independent security review.
8. Explicit Owner approval for any live read-only trial.
