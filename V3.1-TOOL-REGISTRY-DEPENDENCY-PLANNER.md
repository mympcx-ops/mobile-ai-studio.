# V3.1 Tool Registry and Dependency Planner

## Purpose
Continue the phone-first agent-building flow after Prompt-to-Agent. A saved blueprint can be analyzed against a deterministic local capability registry. The planner maps tool IDs, lists prerequisite dependency proposals, and identifies capabilities blocked by policy or missing security gates.

## Behavior
- Reads saved Prompt-to-Agent drafts from this browser's existing local storage key.
- Maps known capability IDs to a versioned local registry.
- Lists required runtimes, connectors, schemas, permissions, sandbox components and approval gates.
- Saves a local Owner-review proposal and exports a readiness JSON report.
- Unknown tool IDs are ignored rather than guessed.

## Hard boundaries
- Availability remains NOT_CONNECTED / NOT_CHECKED because no trusted PC registry is connected.
- No network discovery, package installation, tool grant, host filesystem write, shell execution, model dispatch, agent execution, publish or deploy occurs.
- Shell and host-write capabilities remain disabled; Quinn model dispatch remains blocked pending authenticated pairing, Tool Broker implementation and independent security review.
- A readiness plan is not evidence of installed dependencies or a validation pass.
- Owner approval and independent validation remain required before activation.

## Next integration gates
1. Finish independent review and implementation of authenticated phone-to-PC pairing.
2. Add a read-only, authenticated Tool Broker registry query.
3. Compare requested capabilities with host-verified availability and pinned dependency manifests.
4. Propose missing dependencies for explicit Owner approval; install only through a separately scoped sandbox workflow.
5. Capture execution evidence, run independent validation, and require Owner approval before activation.
